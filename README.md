# Трекер задач

SPA с авторизацией по JWT и CRUD-операциями над задачами: **Vue 3 (Composition API) + Vite + Pinia + Vue Router + Axios + Tailwind CSS**, TypeScript в strict-режиме. Бэкенд эмулируется `json-server` с плагином `json-server-auth`.

## Требования

- Node.js 22+
- npm

## Запуск

Нужны два процесса: mock-api и dev-сервер Vite.

### 1. mock-api (порт 3001)

```bash
cd mock-api
npm install
npm run server
```

Тестовый пользователь `test@test.com` / `12345678` уже лежит в `mock-api/db.json`. Если вы очистили коллекцию `users`, создайте его заново:

```bash
curl -X POST http://localhost:3001/register -H "Content-Type: application/json" -d '{"email":"test@test.com","password":"12345678"}'
```

### 2. Фронтенд

В отдельном терминале, из корня репозитория:

```bash
cp .env.example .env
npm install
npm run dev
```

Приложение поднимется на http://localhost:PORT

```
│   ├── auth/               # LoginForm
│   ├── layout/             # AppHeader
│   ├── tasks/              # TaskBoard (контейнер), фильтры, список, карточка, формы
│   └── ui/                 # BaseModal, AppNotifications, AppErrorBoundary
├── composables/            # useDebouncedSearch, useNotifications
├── constants/              # подписи и стили статусов и приоритетов
├── plugins/                # сборка приложения: обработчик ошибок и истёкшая сессия
├── router/                 # маршруты и навигационные guard'ы
├── stores/                 # Pinia: auth, tasks (setup-синтаксис)
├── test/                   # стаб localStorage, фабрики и app-контекст для тестов
├── utils/                  # auth-storage, errors, date
├── views/                  # LoginView, TasksView — тонкие страницы
└── types.ts                # общие типы домена
```

Компоненты не делают HTTP-запросов напрямую: они работают со сторами, а те — с API-клиентом. Единственное место, где приложение собирается воедино, — `src/main.ts`.

## Как устроены ключевые механизмы

**Авторизация.** `POST /login` возвращает `accessToken`, он вместе с email кладётся в `localStorage`, поэтому сессия переживает F5. Request-интерсептор подставляет `Authorization: Bearer <token>` в каждый запрос.

**Сборка API-клиента.** `createApiClient({ baseURL, getToken, onUnauthorized })` создаёт axios-инстанс с интерсепторами и возвращает готовые группы вызовов (`auth`, `tasks`). Зависимости приходят аргументами, поэтому слой не знает ни про `localStorage`, ни про router и store — их подставляет `src/main.ts` и кладёт клиент в `app.provide`. Сторы получают его через `useApiClient()`: `inject` работает и внутри setup-стора, так как Pinia выполняет setup в контексте приложения. Плюсы против глобального колбэка вроде `setUnauthorizedHandler`: нет мутируемого состояния модуля, каждый тест собирает свой изолированный клиент, а подмена реализации в тестах — это обычный `provide`, а не `vi.mock`.

**Обработка 401.** Response-интерсептор вызывает `onUnauthorized` — им работает `createSessionExpiryHandler` из `src/plugins/session.ts`: пользователь разлогинивается, стор задач очищается, показывается уведомление «Сессия истекла» и происходит переход на `/login`. Прикладная политика вынесена из `main.ts`, поэтому её можно протестировать без поднятия приложения. Запросы к `/login` и `/register` из этой логики исключены, чтобы неверный пароль не выглядел как истёкшая сессия. Токен json-server-auth живёт 1 час, так что сценарий реальный.

**Непредвиденные ошибки.** Два рубежа поверх обработки ошибок в сторах. `AppErrorBoundary` оборачивает `RouterView` и на `onErrorCaptured` показывает запасной экран вместо белой страницы; ошибка дальше не всплывает, поэтому дубля уведомления не будет, а смена маршрута (`resetKey`) снимает экран. Всё остальное — ошибки вне рендера и необработанные промисы — ловит `registerErrorHandler` в `src/plugins/error-handler.ts` через `app.config.errorHandler` и `unhandledrejection`: пишет в консоль и показывает уведомление. Это же место для подключения Sentry.

**Маршруты.** `/tasks` помечен `meta.requiresAuth`, `/login` — `meta.onlyGuest`; `RouteMeta` расширен через `declare module`, флаги типизированы. Сам guard живёт в `src/router/guards.ts`, отдельно от создания роутера — так его можно тестировать без history и DOM. При заходе на защищённый маршрут без токена в query подставляется `redirect`, и после логина пользователь возвращается туда, куда шёл.

**Список задач.** Фильтр по статусу и поиск по названию считаются в геттере стора, ввод дебаунсится на 300 мс (`useDebouncedSearch`). Состояния разведены: скелетон при загрузке, сообщение об ошибке с кнопкой «Повторить», отдельные заглушки для «задач ещё нет» и «по фильтрам ничего не найдено».

**Ошибки API.** Ошибки списка показываются inline с возможностью повторить запрос, ошибки мутаций — всплывающими уведомлениями; молча ничего не проглатывается. Англоязычные ответы json-server-auth («Incorrect password» и подобные) переводятся на русский в `src/utils/errors.ts`, недоступность сервера отличается от прочих ошибок по коду `ERR_NETWORK`.

## Тесты

Unit-тесты на Vitest покрывают логику: утилиты, композаблы, оба стора, API-клиент, глобальный обработчик ошибок и навигационный guard. Рендер компонентов не проверяется, поэтому окружение — `node`, без jsdom; единственная веб-апишка в коде, `localStorage`, подменяется стабом из `src/test/setup.ts`.

```bash
npm test            # один прогон
npm run test:watch  # в режиме наблюдения
```

Тесты лежат рядом с кодом в папках `__tests__` и типизируются вместе с приложением, поэтому `npm run build` проверяет и их. Что покрыто:

- **Стор авторизации** — вход сохраняет токен и email в `localStorage` (сессия переживает F5), ошибка входа переводится на русский и не пускает внутрь, повторная попытка сбрасывает прошлую ошибку, `logout` чистит и состояние, и хранилище.
- **Стор задач** — загрузка списка, сортировка от новых к старым, фильтр по статусу и поиск без учёта регистра, все CRUD-операции, блокировка карточки через `pendingIds` и то, что на 401 стор намеренно молчит, оставляя разлогин интерсептору.
- **API-клиент** — подстановка заголовка `Authorization`, вызов `onUnauthorized` на защищённом запросе и его отсутствие на `/login`, `/register` и прочих статусах; отдельно проверено, что соседние клиенты не делят состояние. Сеть не мокается: подменяется адаптер axios, поэтому цепочка интерсепторов работает целиком.
- **Глобальный обработчик ошибок** — уведомление на ошибке компонента и на необработанном промисе, молчание на 401 (его уже обработал интерсептор), запись в консоль с указанием источника.
- **Истёкшая сессия** — разлогин, очистка задач, уведомление и редирект на `/login`; для уже неавторизованного пользователя обработчик не делает ничего.
- **Guard** — редиректы гостя и авторизованного, включая запоминание адреса в `query.redirect`.
- **Композаблы** — дебаунс поиска на фейковых таймерах (включая снятие таймера при остановке scope) и автозакрытие уведомлений.
- **Утилиты** — разбор ошибок axios (сетевая, строковое тело, тело-объект, фолбэк) и форматирование даты.

## Принятые решения и расхождения с заданием

1. **Эндпоинты `/tasks` не защищены «из коробки»** — вопреки формулировке в задании. В json-server-auth 2.1.0 guard-мидлвары навешаны на пути с префиксом кода доступа (`/660/tasks`), а сам префикс появляется только из файла правил. Поэтому добавлен `mock-api/routes.json` и флаг `-r` в скрипте запуска:

   ```json
   { "users": 600, "tasks": 660 }
   ```

   Код `660` — доступ только для авторизованных и на чтение, и на запись. Владельческие режимы (`600`, `640`) не подходят: они требуют поля `userId` у каждой задачи, которого нет в `db.json`, и тогда даже `GET /tasks` отвечает 403. Как следствие, задачи общие для всех пользователей — привязку к владельцу задание не требовало.

2. **Поиск и фильтрация выполняются на клиенте.** Синтаксис серверного поиска у json-server различается между версиями (`title_like` против `title`), а по условию поиск должен работать по вводу без кнопки — при небольшом списке фильтровать локально и надёжнее, и отзывчивее.

3. **Email берётся из ответа сервера, а не из формы.** `json-server-auth` 2.1.0 на `/login` и `/register` возвращает `{ accessToken, user }` — это проверено по исходнику плагина, поэтому поле `user` в типе обязательное и шапка показывает канонический email из ответа.

4. **Валидация пароля в форме — только на непустое значение.** Сервер требует минимум 4 символа, и дублировать это правило на клиенте смысла нет: решает всё равно бэкенд, а его сообщение показывается пользователю.

## Не реализовано

- **Realtime через WebSocket.** У `json-server` нет WS-канала, поэтому предлагаемый подход такой: в сторе задач выделить идемпотентные мутации `applyRemoteTask(task)` и `removeRemoteTask(id)`, которые обновляют список по данным извне, и подписывать на них композабл `useTasksRealtime`. Сам канал скрыть за узким адаптером с событиями `created` / `updated` / `deleted`: в разработке его можно эмулировать через `BroadcastChannel` (синхронизация между открытыми вкладками) или периодический перезапрос, а при появлении настоящего бэкенда заменить реализацию адаптера на нативный `WebSocket`, не трогая стор и компоненты.

## Проверка сценариев вручную

- **Защита маршрутов.** Открыть `/tasks` без входа — редирект на `/login`; после входа возврат на `/tasks`. Открыть `/login` уже авторизованным — редирект на `/tasks`.
- **Сохранение сессии.** После входа нажать F5: пользователь остаётся авторизованным.
- **Истёкший токен (401).** В консоли DevTools выполнить `localStorage.setItem("tt:access-token", "broken")`, затем сменить статус любой задачи. Ожидаемо: уведомление «Сессия истекла», редирект на `/login`, ключи `tt:access-token` и `tt:email` удалены.
- **Недоступный сервер.** Остановить mock-api и нажать «Повторить»: появится сообщение о недоступности сервера, а не пустой список.
